关键点：

  • 分支 事务使用 @Transactional。
  • 全局 事务使用 @GlobalTransactional。
  • 全局事务服务（比如采购模块）不需要 @EnableTransactionManagement，因为它不需要本地事务管理。

⚡ 六、打通远程链路

在实际生产环境中，分布式事务往往会出现“部分成功、部分失败”的情况。Seata 的两阶段提交（2PC）机制可以确保所有参与者在最终提交或回滚前保持一致。若你在调试时发现部分回滚不生效，检查：

  • 参与者是否正确注册到 Seata
  • 是否使用了 @GlobalTransactional 并且开启了 seata.enabled=true
  • 事务日志是否正常写入（查看 Seata 服务器日志）

🏗️ 七、架构原理

  • Client：微服务调用者，发起全局事务。
  • Seata Server：负责全局事务管理、锁管理、事务日志。
  • Resource Manager：数据库或其他资源，参与本地事务。
  • Transaction Manager：协调两阶段提交。

🔎 八、原理细节

📑 二阶段提交协议（2PC）

  1. Prepare（准备）

    • Client 发起全局事务，Seata Server 为每个参与者生成 global_tx_id。
    • 参与者执行本地事务并暂时锁定资源，返回 prepare OK。

  2. Commit/Abort（提交/回滚）

    • Seata Server 收到所有 prepare OK 后决定提交或回滚。
    • 对所有参与者发出 commit 或 rollback 命令。
    • 参与者执行对应操作并释放锁。

🔄 九、四种事务模式

模式适用场景关键特点代码示例
AT传统 CRUD 业务本地事务 + Seata 全局事务，行锁释放快@Transactional + @GlobalTransactional
XA高一致性需求事务执行期间全局锁 + 行锁，性能略低@Transactional + @GlobalTransactional，但需要开启 XA
TCC需要手工补偿的业务（如发短信、发送邮件）预留、确认、补偿三个步骤@Transactional + 自定义 try/confirm/cancel
SAGA长事务、业务流程拆分基于消息队列，避免长时间锁@Transactional + 事件驱动

AT vs XA：

  • AT：第一阶段执行完 SQL 后即释放行锁，锁持有时间短。
  • XA：行锁在第二阶段才释放，导致锁持有时间长，性能下降。
  • 两者都持有 Seata 的全局锁。

TCC：适合“事务不止数据库”场景，缺点是需要手工补偿代码。
SAGA：适合业务流程拆分、长事务，使用消息队列实现补偿，系统解耦更好。

小结：大多数 CRUD 业务推荐 AT；需要高度一致性可考虑 XA；业务涉及外部系统则使用 TCC；长事务则使用 SAGA。

🎉 结语

通过 Seata 的两阶段提交和四种事务模式，你可以在微服务架构中轻松实现可靠的分布式事务。别忘了根据业务特点选择合适的模式，既能保证一致性，又能保持系统性能。
